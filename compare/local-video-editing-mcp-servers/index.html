Local video editing MCP servers for AI agents, and hosted alternatives: 7 compared

As re-checked on 25 October 2026, four of the seven video editing tools for AI agents compared here are local MCP servers that edit your files: Cutbolt (ours; 18 tools listed by default, 86 in full), Kinocut (formerly mcp-video; 203), claudeclip (31) and ffmpeg-skill (42, 12 listed by default). On one Windows PC we ran Cutbolt over MCP and ffmpeg-skill's cut on the same 720p test clip: both cut exactly the expected 150 source frames and wrote byte-identical files on repeat runs with one FFmpeg build, and Cutbolt also keeps a saved timeline with revisions, safe retries and undo, while ffmpeg-skill writes a new file per call. The other five (Kinocut, claudeclip, Video Jungle MCP, Vlexor and HyperFrames) we read from their code and docs at their latest release or commit, without running them: Video Jungle MCP edits on Video Jungle's servers, Vlexor has a hosted engine plan each edit and renders it on your machine, and HyperFrames renders new videos from HTML, with no local MCP server for desktop agents. Resending the same edit request to Cutbolt returned its original receipt and undo restored the earlier cut; resending ffmpeg-skill's cut to the same path was refused and left the file untouched, so neither applied an edit twice, but the agent got an error rather than its earlier result. We also measured Cutbolt's 0.4.0 release exactly as downloaded. The page was first published on 17 October; method, sources and data are below.

We make Cutbolt. Read this as a vendor's page: our own numbers come from runs you can repeat, and everything about the other tools links to where we read it. If we got something wrong, open an issue and we will correct it.

The short answer: which video editing MCP server to use

  • You have real footage (interviews, talking heads, tutorials, screen recordings) and want an agent to cut, caption, mix and export it, then revise, retry or undo its edits, on your own machine with no account: Cutbolt. It keeps every edit as a saved revision, and we measured frame-exact cuts and repeatable exports (main fixes a repeatability case that the 0.4.0 release still has). You install FFmpeg yourself, and MCP exports need Windows or Linux (the macOS build can't run them). It is young: version 0.4.0 and 1 GitHub star.
  • You want the most tools of the seven compared here (203), in Python, with quality gates, receipts and optional AI extras (transcription, upscaling, HTML graphics): Kinocut, with 221 GitHub stars and regular releases (three since 17 October).
  • You want an agent to run separate editing jobs (cuts, captions, reframing, loudness, delivery checks) with a large, documented FFmpeg tool set and nothing to run but Python and FFmpeg (its npx installer also needs Node.js): ffmpeg-skill, with about 2,770 GitHub stars. We ran its cut with --accurate: frame-exact on our clip, like Cutbolt's. It keeps no revisions or undo: each call writes a new file, or a project.json you edit is rendered again.
  • You want quick one-off jobs (trim, convert, make a GIF, burn in subtitles, even out loudness) from one npx line, with FFmpeg fetched for you: claudeclip.
  • You want to make new videos, such as motion graphics, explainers or launch videos, rather than edit footage: HyperFrames. It installs as a Claude Code plugin and a CLI; its MCP connector is hosted by HeyGen and needs a HeyGen account.
  • Your footage lives in Video Jungle, or you want hosted search and edits with a hand-off to DaVinci Resolve Studio: Video Jungle MCP, with a Video Jungle account and API key.
  • Vlexor: on 17 and again on 25 October its package could not be installed as its README says, and its site said it was being rebuilt. Check it before you rely on it.

What we measured on Cutbolt

25 October 2026: the release as you download it, and today's main

On 17 October we built Cutbolt from source (below). On 25 October we ran the same probe on the 0.4.0 release exactly as people download it, on the same machine with the same FFmpeg build:

  • The download: the Windows zip from the v0.4.0 GitHub release and the Windows MCPB bundle both matched their published SHA-256 checksums, and the cutbolt.exe inside each was byte-identical; it reports commit e668c16, the tag (hashes).
  • MCP tools: it lists the same 18 tools by default and with --tools core, the mode the MCPB bundle starts it in (21,198 bytes, as on 17 October), and 86 with --tools full (lists). The bundle's own manifest declares the same 18 (listed in the hashes file): its build step lists the tools from the server and takes only their descriptions from the repository's mcpb/manifest.json, a build template whose 32 entries include tools the build drops.
  • Three runs on the colour-coded clip and two on the moving pattern: every exported frame and both previews were the expected source frames, the resent request kept revision 1, undo restored revision 0, and the source file was unchanged. Every H.264 export had the same SHA-256 as the matching export from our 17 October source build of 0.4.0, on both clips (summary and comparison). Median times were within 1 ms of 17 October's for the session calls and within 7% for inspection, previews and exports.
  • Today's main: 1f4058c. Its three commits since ddc77c9 change docs, skill recipes, plugin files, a security policy and evaluation cases, not the engine's source or Cargo files. We built it (1 min 46 s, build) and ran one probe on each clip: the same 18 and 86 tools, the same checks passing, and the same export bytes as ddc77c9 (colour run, moving-pattern run, tool lists). Cutbolt's skills check passed on it in 40 s (output).
  • The Claude Code plugin needs main: the plugin (added to the repository on 18 October) uses main's skill recipes, and Cutbolt's README says to build main from source for it. We checked why: run against the 0.4.0 download, the same skills check stopped at the first recipe, whose render step sends a mode argument that 0.4.0 doesn't accept (output).

Scripts added: cutbolt_tools_modes.py (tool lists in each mode) and cutbolt_summary_release.py (the summary and comparison). Runs: release download 1, 2, 3, moving pattern 1, 2.

17 October 2026: 0.4.0 and main built from source

On 17 October 2026, on one machine: Windows 11 Pro (build 26200), an AMD Ryzen 9 7950X3D, Rust 1.98.1, FFmpeg 7.0 (the gyan.dev full build), no GPU work. We built two versions from source with cargo build --release --locked: the 0.4.0 release (tag v0.4.0, e668c16, 1 min 45 s), which is what the release downloads and the MCP Registry entry ship, and main at ddc77c9 (1 min 53 s), 40 commits later (0.4.0 build, main build). We drove each over MCP stdio from a small Python client, the way an agent's MCP client does. Every result below held on both builds unless it says otherwise.

  • Tests (main): cargo test --release --locked passed 261 of 261 Rust tests in 10.8 s (output, compile lines removed). Cutbolt's own check of the recipes in its six agent skills, python -X utf8 tools/verify.py --only skills --no-rust --engine target/release/cutbolt, passed in 33 s (output, temporary path removed); its installation guide says this check runs every JSON request in the skills against synthetic footage. We didn't re-run its longer acceptance suite, or the tests on 0.4.0.
  • MCP tools: both builds list 18 tools by default: session create, get, apply, undo, history and receipt; job start, wait, status, cancel and resume; schema; files list; media inspect; timeline check; cache inspect and prune; and cutbolt_run, which runs the other 69 commands by name. The tools/list reply is 21,198 bytes on 0.4.0 and 22,726 on main. mcp --tools full lists all 86 tools directly, in 235,843 and 240,088 bytes (lists: 0.4.0 default and full, main default and full).
  • The test clip: 10 s of 1280×720, 30 fps H.264 (High, 4:2:0) with stereo 48 kHz AAC, made with FFmpeg so that every frame has its own flat colour. Reading a frame's colour back gives its source frame number, so we could check every exported frame independently of Cutbolt.
  • The edit, over MCP: inspect the clip; create a saved project keeping source seconds 0–3 and 5–8, picture and sound linked (6 s); preview the frame at 3 s; ripple-delete timeline seconds 1–2 (5 s); send that same edit request again; preview the frame at 1 s; export H.264/AAC twice and a lossless reference once; undo; export again. We ran it three times per build, each in a new folder. Median times on main: inspect 535 ms, create 14 ms, the ripple delete 6 ms, the resent request 1 ms, undo 7 ms, a frame preview 311–374 ms, an H.264 export of the 5-second cut 1.9–2.0 s from queueing the job to its finished receipt, and 3.3 s for the lossless one. On 0.4.0 the session calls were within 0.5 ms of these, and inspection, previews and exports within 4%.
  • Frame-exact: in all six runs, the 150 frames of every export of the cut were source frames 0–29, 60–89 and 150–239, in order, with none missing or repeated; after undo, the 180 exported frames were 0–89 and 150–239. Both previews showed the right source frame (150 and 60). Each MP4's AAC track lasted exactly as long as its picture: 5.000 s and 6.000 s.
  • Safe retries: resending the identical edit request, with the same request ID, returned its original receipt and revision 1, and the saved project stayed at revision 1 rather than applying the cut twice. Cutbolt's docs say the same ID with different arguments is refused, and a new ID is a new edit.
  • Undo: session.undo saved revision 2, identical to revision 0 apart from its number, and session.history listed all three revisions.
  • Repeatable exports: on the colour-coded clip, all 12 H.264 exports of the cut (two per run, three runs per build) had the same SHA-256. Because flat colours are easy for an encoder, we repeated the edit twice per build on FFmpeg's moving testsrc2 pattern: within each build, all four H.264 exports were byte-identical, while 0.4.0's bytes differ from main's, because on 14 October main switched x264 to its CPU-independent mode after exports of identical frames from a small moving sample decoded differently (see Cutbolt's limits below). The frames fed to the encoder were the same on both builds. The lossless .mkv files differed byte for byte from run to run, but their decoded pictures and sound did not: FFmpeg's own hash of each run's decoded RGB frames and PCM audio was the same on all six runs, and equal to the hashes in Cutbolt's H.264 receipts of the frames and samples it fed the encoder (hashes). All of this was one FFmpeg build: like Kinocut, Cutbolt doesn't promise identical bytes across FFmpeg builds.
  • Source preserved: the source file's SHA-256 was the same before and after every run, and matched the hash Cutbolt reported when it inspected the file.

Data: summary and medians; colour-coded runs on 0.4.0 1, 2, 3 and on main 1, 2, 3; moving-pattern runs on 0.4.0 1, 2 and on main 1, 2 (frame-number checks don't apply to this clip and read false). Scripts: cutbolt_probe.py (the MCP round trip), cutbolt_frame_ids.py (reads frame numbers back) and mcp_session.py (a minimal MCP client).

To repeat it you need Rust, a C compiler and linker (for the bundled SQLite), Python 3 and FFmpeg 7 on PATH. Clone and build Cutbolt, put the three scripts in the Cutbolt folder, then make the clip and run the probe there:

git clone https://github.com/skulitom/Cutbolt
cd Cutbolt
git checkout v0.4.0
cargo build --release --locked
# download cutbolt_probe.py, cutbolt_frame_ids.py and mcp_session.py into this folder
mkdir run1
ffmpeg -f lavfi -i "color=c=black:s=1280x720:r=30:d=10,format=gbrp,geq=r='mod(N\,16)*16+8':g='floor(N/16)*12+8':b='64',scale=out_color_matrix=bt709:out_range=tv,format=yuv420p" -f lavfi -i "sine=frequency=440:sample_rate=48000:duration=10" -ac 2 -c:v libx264 -profile:v high -preset medium -crf 12 -g 30 -bf 2 -colorspace bt709 -color_primaries bt709 -color_trc bt709 -c:a aac -b:a 192k -movflags +faststart run1/source.mp4
python cutbolt_probe.py target/release/cutbolt ffmpeg ffprobe run1 run1-result.json

Use a new folder holding a copy of source.mp4 for each run. To test main, run git checkout ddc77c9 (or 1f4058c, the 25 October main, with the same engine code) and cargo build --release --locked again. On Windows, use cutbolt.exe and full paths to ffmpeg.exe and ffprobe.exe. With our FFmpeg build the clip hashed 4ded9771…, and the moving pattern ca010470… (both in full in the summary); file hashes match ours only with the same FFmpeg build, while the frame, retry and undo checks and the run-to-run comparisons don't depend on it. For the moving pattern, replace the first input with -f lavfi -i "testsrc2=s=1280x720:r=30:d=10" and use -vf "scale=out_color_matrix=bt709:out_range=tv,format=yuv420p"; then only the hash comparisons apply. The hashes file gives the FFmpeg commands for the decoded-stream hashes. To test the release as downloaded instead of building it, run gh release download v0.4.0 -R skulitom/Cutbolt (or download from the release page), check the files against SHA256SUMS, unpack the Windows zip and pass its cutbolt.exe to the probe; on 25 October both clips hashed as above with the same FFmpeg build.

Each tool, and when to choose it over Cutbolt

Kinocut (formerly mcp-video)

KyaniteLabs/kinocut (PyPI kinocut 1.16.4, 24 October 2026) is the project that directory listings still show as mcp-video under pastorsimon1798 or KyaniteLabs: those addresses redirect to the same repository, and the mcp-video package on PyPI (1.6.19) now just installs Kinocut. It is a Python server whose source registers 203 tools: trimming, merging, effects, overlays, subtitles, audio mixing and loudness, a JSON timeline spec, projects and replayable recipes, OTIO import and export, quality gates, and optional AI tools such as Whisper transcription and upscaling, plus wrappers for HyperFrames. Multi-step workflows write receipts with SHA-256 of each step's inputs and outputs and can resume; its README says rendered bytes may vary across FFmpeg builds. Since 1.16.3 it won't replace an existing media output unless the call says overwrite=true. Its FFmpeg tools need no account, but some tools fetch from the network: a video URL given to video_analyze is downloaded with yt-dlp, and missing Google Fonts and model weights are downloaded on demand. Since 1.16.4 its optional AI image analysis is off by default; an operator can send images to Anthropic's API (with a key), to another Anthropic-compatible endpoint, or to a local server, and it turns off the telemetry of the HyperFrames and Revideo renderers it starts. It also ships plugin files for Claude Code and other agents. The repository has 5,846 test functions and CI. We read its 1.16.4 release, the version you install.

Choose it when you want the largest tool set compared here (203 tools), in Python, AI extras such as transcription and upscaling, or HTML graphics through HyperFrames, from an active project with a large test suite. Choose Cutbolt when the agent will revise an edit many times: every edit is a saved revision with undo, resending a request with the same ID returns its original receipt instead of applying it again, cuts landed on exact frames in our test (we didn't test Kinocut's), and the default tool list is 18 tools rather than 203.

claudeclip

gulkoa/claudeclip (npm claudeclip 1.2.1) is a TypeScript server with 31 tools that each run one FFmpeg command on a local file: trim (a frame-accurate re-encode or a fast copy), join, speed, resize, crop, convert, GIF, overlays, picture in picture, burning in an SRT or ASS file, EBU R128 loudness, scene and silence detection, and a contact sheet of frames so the agent can see the video. Outputs never overwrite a file and, unless you name one, land next to the input. Installing it downloads an FFmpeg 6.1.1 build through the ffmpeg-static package, and it uses your own FFmpeg when it finds one. It keeps no project or undo history. Its CI runs a smoke test that calls every tool on three operating systems. All its commits so far came from one author on 4 August 2026.

Choose it for quick, single-step jobs from one npx line, especially when you don't have FFmpeg installed. Choose Cutbolt for an edit made of many cuts you will revisit: a saved multi-clip timeline with linked picture and sound (frame-exact in our test), captions from transcripts, and undo.

ffmpeg-skill (new on this page on 25 October)

kajisho5/ffmpeg-skill (npm ffmpeg-skill 2.16.1, 24 October 2026; about 2,770 GitHub stars, created 3 September 2026) is an agent skill and a local MCP server: a SKILL.md that teaches a probe, edit and verify workflow, 42 Python tools on FFmpeg (cuts and joins, silence removal, reframing, captions and karaoke, overlays and graphics, HDR to SDR, colour, audio clean-up, sync, multicam, loudness, delivery checks, and rendering a JSON project), and mcp/server.py, which lists 12 of them by default and runs each call as its own script. It uses only Python's standard library, needs no account or key, and its own code makes no network calls; its optional transcription uses a speech engine you install, which downloads its model on first use. The tool keeps no revisions or undo: each call writes a new file, it refuses to replace an existing output unless told to, and a whole edit can be kept as a project.json you change and render again. Its README reports its own agent evaluations (not checked by us).

We ran its cut. It meets our rules for running another tool in what we used: open source, offline, no account or key, no network or desktop access. From its npm package (its gitHead is the release tag), on the same machine, test clip and FFmpeg build as Cutbolt, we ran its cut tool the way its MCP server runs each call, keeping source seconds 0–1, 2–3 and 5–8: the same final cut as Cutbolt's revision 1 above. cut.py source.mp4 --segments 0-1,2-3,5-8 --accurate -o out.mp4 --json gave, in three runs, 150 frames that were all the expected source frames, 5.000 s of audio and byte-identical files. Without --accurate, it stream-copies when it can, so a cut may start up to 0.5 s early at a keyframe (it reports the precision it reached); on our clip it found that the frames are reordered (B-frames), re-cut every segment from the source instead, and wrote the same file. Sent again to the same output path, the cut was refused ("refusing to overwrite existing output") and the file left untouched: it can't apply twice, but the agent gets an error rather than its earlier result. Both encoded video with x264 at CRF 18, preset medium (audio: AAC at 192 kb/s for ffmpeg-skill, 320 kb/s for Cutbolt). ffmpeg-skill's cut took 0.94–1.00 s from start to exit; Cutbolt's export of the same cut took 1.9–2.0 s from queueing the job to its finished receipt, about twice as long. The work differs: Cutbolt's export also decodes the file it wrote to check its frame and sample counts and hashes, while ffmpeg-skill probes its output. So this is one clip on one PC, not a speed benchmark. Data: package check; runs with --accurate 1, 2, 3 and without 1, 2; the resend; script ffmpeg_skill_cut_probe.py. To repeat it: npm pack ffmpeg-skill@2.16.1, unpack it into its own folder, make the colour-coded clip as above, put ffmpeg_skill_cut_probe.py next to cutbolt_frame_ids.py, and run python -I ffmpeg_skill_cut_probe.py package ffmpeg ffprobe source.mp4 out accurate 3 --resend --accurate (and ... default 2 for its default mode).

Choose it when the agent should run editing jobs on files with a large, documented FFmpeg tool set (delivery checks, captions, HDR, multicam), from a popular, active project that needs nothing but Python and FFmpeg to run; in our test its cut with --accurate was as frame-exact as Cutbolt's. Choose Cutbolt when the agent will revise one edit over many steps: a saved multi-track timeline with revisions and undo, where resending a request with the same ID returns its original receipt, rather than a new file per call.

Video Jungle MCP (burningion/video-editing-mcp)

burningion/video-editing-mcp (PyPI video-editor-mcp 0.1.59) connects an agent to Video Jungle, a hosted video service: uploading videos, searching them by what is said, generating edits, and rendering them on Video Jungle's servers. It needs a Video Jungle account and API key. Its edit-locally tool downloads an edit's assets, builds an OTIO timeline and imports it into DaVinci Resolve Studio, which must already be running. At startup it downloads the jina-clip-v1 model from Hugging Face and runs that model's own code, and it opens Video Jungle's web app in your browser after edits. The repository has no licence file.

Choose it when your footage is in Video Jungle, or you want hosted search across your videos and a hand-off to DaVinci Resolve Studio. Choose Cutbolt when footage must stay on your machine, with no account, no browser and no desktop app in the loop.

Vlexor MCP

Open2Loop/vlexor-mcp has 6 tools. Its generate_edit_plan sends your instruction (and any transcript) to Vlexor's hosted engine, which counts against your plan's usage; compile_edit_plan and render then build and run an FFmpeg command on your machine, with burned-in captions as an option. It needs a Vlexor API key to start. On 17 October 2026, and again on 25 October, the package its README tells you to run, @velxor/mcp, returned 404 on npm, the repository depends on private packages and can't be built on its own, Vlexor's home page said it was being rebuilt, and its pricing page returned 404. Its terms describe Pro, Pro+ and Max plans with monthly caps on AI-editing minutes.

Choose it, once it can be installed again, for edits planned by a hosted AI from plain-language instructions and rendered locally. Choose Cutbolt for an engine you can install today, with no account or usage limits, where the agent itself decides each edit.

HyperFrames

heygen-com/hyperframes (npm hyperframes 0.8.198, 25 October 2026; about 71,900 GitHub stars) turns HTML, CSS and JavaScript into video: headless Chrome captures each frame and FFmpeg encodes them. It ships a CLI, a Claude Code plugin and 7 agent skills (on 21 October it replaced its workflow skills, 21 when we first checked, with 7 knowledge skills); captions and audio mixing are covered in its media skill. It has no local MCP server for desktop agents: its MCP is a hosted connector, in beta, that needs a HeyGen account and renders on HeyGen's infrastructure, and its Studio app exposes WebMCP tools (an early browser feature) to an agent running in the browser. Its CLI sends usage data to PostHog by default, which you can turn off (hyperframes telemetry disable, HYPERFRAMES_NO_TELEMETRY or DO_NOT_TRACK). It releases several times a day: 28 versions on npm after the 0.8.168 we first read, up to 0.8.198 on 25 October.

Choose it to make new videos (motion graphics, explainers, launch videos, animated captions) from code models already write well, with a large community behind it. Choose Cutbolt to edit footage you recorded: cuts, ripple deletes, linked sound, multicam, OTIO hand-off and loudness, all through a local MCP server. The two can work together: Cutbolt's command line can compile a rendered PNG sequence with transparency into a lossless movie (image.sequence.compile, not an MCP tool), and an alpha_over track places it over your footage; on main, a transparent ProRes file can be placed through automatic preparation.

Cutbolt's limits

  • It edits footage you already have. It doesn't generate video from a prompt, and it has no visual timeline for editing by hand: an agent, JSON commands or the Rust library drive it.
  • FFmpeg and ffprobe must already be installed; Cutbolt neither bundles nor downloads them.
  • Windows and Linux are its tested platforms. The macOS (Apple silicon) build exists, but background jobs, which MCP exports go through, need Windows or Linux, and native audio recording and hardware decoding need Windows.
  • Footage goes on the timeline as it is only when it is even-sized, 8-bit 4:2:0 H.264 or HEVC at the project's exact size and frame rate; other formats are converted first. On main (since 13 October) a queued export does that automatically; in the 0.4.0 release you prepare them explicitly first. The timeline works in 8-bit SDR by default, and anything outside its documented limits fails with an error rather than a guess.
  • In the 0.4.0 release, repeated H.264 exports of the same frames can occasionally differ: Cutbolt's own 0.4.0 notes record an open, intermittent difference, and on 14 October eight encodes of a small moving sample with its settings gave three different results. main fixed this that day by switching x264 to its CPU-independent mode. Our 0.4.0 runs didn't hit it.
  • Speech recognition, for cutting your own recordings by transcript, is optional and needs a separately installed Python and model setup; its tested setup used WSL and an NVIDIA GPU. Without it, transcript edits need a transcript you supply.
  • It is young: version 0.4.0 (12 October 2026, still the latest release on 25 October), 1 GitHub star, not on crates.io. Install it from the release archives or from source; the Claude Code plugin needs main built from source, because at least one of its recipes sends an argument the 0.4.0 release doesn't accept. It is in the official MCP Registry as io.github.skulitom/cutbolt.

Method

  • The searches this page answers, first run on 17 October 2026: "local video editing MCP server", "MCP server for video editing local ffmpeg agent" and "best video editing MCP server for Claude Code". On 25 October we ran them again, with two queries Claude agents wrote when we asked them to find a video editing MCP server: "MCP server local video editing ffmpeg cut captions render Claude Code" and "video editing MCP server github trim subtitles burn-in ffmpeg Whisper" (results). Directory pages (Glama, Enterprise DNA, mcpservers.org, LobeHub and others) filled most results; Tella's vendor roundup ranked in three of the five, and JSON2Video's and OpusClip's own pages in one. One summary again said the results include no independent head-to-head tests. Cutbolt appeared in none, on either date.
  • Which tools: mcp-video (now Kinocut) and Vlexor, which ranked for the second search on 17 October; HyperFrames, the most starred tool compared here (about 71,900 stars); claudeclip and Video Jungle MCP, which ranked or were named in the results; and, from 25 October, ffmpeg-skill (about 2,770 stars), which Claude agents named when we asked them to find a video editing MCP server on 22 October and which GitHub search ranks highly; it didn't appear in the five web searches. ffmpeg-mcp-lite, named in three search summaries, stays under "Also": it has 8 single-command tools and keyframe-only trims. The other results, and servers we added for their stars or their design, are under "Also".
  • Cutbolt was built and tested from fresh clones of its 0.4.0 tag and main on 17 October, and on 25 October as the release download and as main again, as described above.
  • Running the other tools. We run another tool only when it is open source from its official source, works offline with no account or key, and can't reach the network or your desktop. On 25 October we ran ffmpeg-skill's cut from its npm package in its own folder, with its optional transcription and hardware encoding left off, on the same clip, machine and FFmpeg build as Cutbolt. claudeclip also meets the rules, but its installation downloads an FFmpeg binary from a third-party release, so we read its code instead and didn't test its cuts. ffmpeg-mcp-lite and Timeline Studio's headless server may meet them too; they are under "Also" and weren't run. We judge the rules on the features we run: Kinocut can fetch from the web through some tools, but its plain FFmpeg trim tool (no URL inputs or downloads) would likely pass that way; we didn't run it this time, and it is first in line for the next check. HyperFrames' CLI sends telemetry by default and can capture websites, Video Jungle MCP and Vlexor need accounts and keys, and Vlexor's package couldn't be installed. For every tool we read the README, the files named below and the hosted services' own pages, and counted MCP tools in each server's source. Stars, releases and package versions come from GitHub, PyPI and npm on the date given.
